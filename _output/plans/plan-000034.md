## User brief

> source: research-000032 — Implement the R1 positive-control sanity battery from research-000032 to determine whether the ~40% capture-rate "ceiling against a random Pacman" is a confound (curriculum-stage misattribution / env-eval artifact / POMDP wall) or a genuine learning limit, BEFORE committing GPU to a hyperparameter sweep. The battery must isolate the truly-random condition: curriculum OFF, --pacman-random-action-prob 1.0, full observability (ghost_view_size unset), research-000022 artifacts neutralized (set --pacman-safe-distance near the ghost view radius; avoid the orbit reward), and a greedy (epsilon=0) capture-rate eval distinct from the training-time on-policy metric so the epsilon-floor measurement bias is ruled out. Scope is the verification battery only (a small set of short runs + the greedy-eval metric/protocol), not the full sweep.

## Agent interpretation

**Problem**: The team believes the ghosts hit a 40% capture ceiling against a random Pacman (which should be ~100% catchable) and wants to pivot to hyperparameter tuning — but research-000032 found the "random Pacman" framing is probably a confound. We need a cheap, reproducible experiment that decides *confound vs genuine learning limit* before any GPU sweep.

**Approach**: Run a controlled A/B over the existing benchmark harness, changing *only the opponent condition*:
- **Condition P (positive control):** the *truly random* opponent in isolation — `--pacman-curriculum off`, `--pacman-random-action-prob 1.0`, full observability (no `--ghost-view-size`), sparse `capture_v0` reward (no orbit term), evaluated greedily.
- **Condition C (the suspect):** the *curriculum-on* config the team has been running (`--pacman-curriculum easy-medium-hard`), evaluated greedily at its checkpoint difficulty (which is the *hard evader*, not random).

If P → ~100% and C → ~40%, the ceiling is a **curriculum-stage misattribution** (proven), not an HP limit → skip the sweep, fix the framing/eval. If P also → ~40%, it is a **genuine learning limit** → the scalar UTD-axis sweep (research-000032 R4) is justified. The greedy eval is supplied by the existing `eval_report.py` deterministic path (`evaluation_deterministic_actions`), which keeps the checkpoint-defined difficulty and emits `capture_rate` — so "greedy ε=0 eval distinct from the training on-policy metric" already exists; we just must set `--eval-episodes > 0` (harness default is 0 → empty DV) and read it back.

Most of the battery runs on **existing CLI flags**; the only new code is two thin, reproducible runbook artifacts (a launcher that pins the flag-set + writes a provenance manifest, and a decision-readout that prints the verdict). The `_pacman_rng` seed-pin (T4) is **already implemented** (pacman_environment.py:244-251, plan-000031/000029), so no env-logic change is needed. At `p=1.0` the Pacman ignores its flee heuristic (uniform random), so the research-000022 RC2 (oscillation saddle) and RC3 (safe-distance cordon) artifacts are auto-neutralized; only RC4 (orbit reward) matters and is handled by the sparse reward-id — so `--pacman-safe-distance` tuning is unnecessary for Condition P.

**Alternatives rejected**:
- *Add a new in-loop greedy eval metric now (research-000032 R7):* deferred — `eval_report.py` already gives a greedy `capture_rate`; building a new in-loop metric is sweep-infrastructure, out of R1's "verification only" scope.
- *Go straight to the scalar sweep (R4):* rejected — that is exactly what research-000032 warns against; spending GPU before the confound is ruled out risks tuning knobs that cannot move a structural wall.
- *Modify the env to neutralize RC2/RC3 explicitly:* rejected — at `p=1.0` they are already moot; an env change would be out of scope and add a confound.

**Selection rationale** (source research-000032):
- Included: R1 — this plan *is* the positive-control sanity battery.
- Included: R2 — Condition C vs P directly tests the curriculum-stage misattribution.
- Included (partial): R3 — full observability is pinned in Condition P; the local-view/POMDP arm is noted as a follow-up, not run here.
- Included: R6 — ≥5 seeds (Q3), explicit seeds (T4), commit hash in the manifest (C1).
- Excluded: R4 — the scalar UTD sweep is the *next* plan, gated on this battery's verdict.
- Excluded: R5 — promoting the epsilon floor to a flag belongs to the sweep, not the verification.
- Excluded: R7 — new in-loop eval metric is sweep infra; the existing greedy `capture_rate` suffices for the DV.
- Excluded: R8 — flag promotion / scope-wording is a sweep concern.

## Best practices

- **Positive/negative controls before measurement** (RL experiment hygiene): never interpret a negative result without a control that must succeed.
- **Provenance for reproducibility** (constitution C1/T4): every run records the commit hash, explicit seeds, and full config in a manifest (reuse the research-000028 sweep-manifest pattern).
- **Change one variable**: P and C differ only in the opponent/curriculum axis; reward-id, obs, frames, seeds, and eval protocol are held identical so the comparison is clean.
- **Deterministic eval**: capture_rate is read from the greedy (`evaluation_deterministic_actions`) eval path, decoupling the DV from the training-time epsilon floor.

## Design decisions

**User-visible impact**: A new `make r1-positive-control` (and the two scripts) lets the researcher run one command and get a printed verdict — "random-Pacman control = NN% capture, curriculum config = NN%; ceiling is/ isn't a confound" — plus an auditable `r1_manifest.csv`. No change to training, the environment, or existing runs.

**Trade-offs accepted**: Gained a decisive, reproducible go/no-go for the sweep at low GPU cost. Gave up immediate progress on tuning (intentional — the verdict gates the sweep). The local-view/POMDP arm (research-000032 R3) is not exercised here; if Condition P clears the ceiling that arm is moot, otherwise it becomes a follow-up.

**Metacommunication impact**: The readout tells you, in plain terms, *which Pacman the 40% was actually measured against* and whether tuning is worth your GPU — so the tool now communicates the experiment's conclusion, not just raw CSV numbers.
