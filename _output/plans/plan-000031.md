## Agent interpretation

**Problem.** The PBRS claim (research-000024) rests on a single-seed `pinklike3` run, which cannot support a causal statement; the project constitution (Q3) requires >=5 seeds, and a credible test of "PBRS accelerates acquisition of pursuit behavior" needs a controlled A/B where the two arms differ *only* in the shaping term. The two existing reward-ids do not satisfy that: `capture_v0` (terminals +45/-40/-45, `timestep -0.015`, plus a `pacman_legal_moves_reduced +1.0` dense term) and `capture_v0_pure_potential_shaping` (terminals +/-100, `timestep -0.05`, plus PBRS) differ in four ways, so comparing them confounds shaping with terminal magnitude, step cost, and an extra dense term.

**Approach.** Build a methodologically clean A/B and the metrics that make the result interpretable, reusing the existing `run_benchmark.py` training path:
1. **Matched sparse control reward** (`capture_v0_sparse_control`) = the PBRS arm with the `potential_shaping` term removed and *everything else byte-identical* (it reuses `CaptureV0PurePotentialShapingWeights`, so terminals +/-100 and `timestep -0.05` cannot drift between arms). This makes the only difference between the two arms the PBRS term -- the precondition for a causal claim.
2. **Pursuit-specific eval metric** (`pursuit_fraction`) = fraction of episode steps where the team's BFS distance to Pacman strictly decreases. `capture_rate` alone cannot distinguish "learned to pursue but rarely closes the kill" from "wanders"; R5 explicitly asks for this.
3. **Sample-efficiency analysis** from the per-run training curve (`live_progress.csvl`): area-under-the-eval-capture-curve (AULC) and frames-to-threshold. This is the *headline* metric, because PBRS is policy-invariant by construction, so the hypothesis is faster acquisition, not higher asymptote.
4. **A/B sweep runner** that loops `p in {0.25,0.50,0.75}` (curriculum off, hard, `--randomize-spawns` on, held constant), invoking `run_benchmark.py` once per `p` with **both** `--reward-ids` into a distinct per-`p` save-folder (avoids the maze/reward/device-only path collision), and writes an auditable manifest with git commit.
5. **A/B aggregator + plotter** producing the comparison table (mean +/- std per arm per `p`) and grouped figures for capture_rate, pursuit_fraction, and the sample-efficiency headline.

**Alternatives rejected.**
- *Use the existing `capture_v0` as the control* (no new reward code): rejected -- it confounds shaping with three other differences (terminals, timestep, legal-moves term), which is exactly the validity gap the "decisive" benchmark is meant to close (user chose the matched control).
- *Implement the control as `CaptureV0PurePotentialShaping(alpha=0)`*: rejected -- it would still emit a `potential_shaping` term of `0.0` every step (noise in the per-term breakdown) and couples the control's correctness to the shaping code path; a dedicated subclass that simply omits the term is clearer and self-evidently sparse.
- *Run the A/B against the fully-evasive hard Pacman (`p=0`)*: rejected by the user in favor of `p in {0.25,0.50,0.75}` -- research-000028 shows `p=0` risks a floor effect (both arms ~0, no signal). The three interior points sit in the learnable regime where a sample-efficiency difference is detectable.
- *Re-implement the p-sweep wrapper / seed-pin from scratch*: avoided -- the seed-pin fix is shared with plan-000029 (declared as a dependency / shared edit, not duplicated), and this plan's runner is a thin A/B-focused loop rather than a second general sweep tool.

**Selection rationale** (source: research-000024):
- Included: R1 -- the PBRS arm already exists; this plan adds its matched control so R1's variant is testable against a baseline.
- Included: R3 -- the control omits all non-potential terms, mirroring R3's "strictly sparse terminals + timestep + PBRS" design on the experimental side.
- Included: R5 -- the >=5-seed A/B, the sample-efficiency framing, and the pursuit-specific metric are the spine of this plan (Steps 2, 4, 5).
- Included: R6 (partial) -- alpha is already tuned (0.7) and fixed; the A/B holds it constant. The `min` vs `mean` ablation is out of scope here (the shipped arm uses `mean`); noted as future work.
- Excluded: R2 (gamma factor) -- already superseded by the shipped exact-`gamma=1` telescoping; nothing to do.
- Excluded: R4 (terminal-vs-timeout potential handling) -- already handled in the shipped PBRS arm; the control inherits the same terminal semantics.

## Best practices

- **Reproducibility-first (constitution T4/Q3):** >=5 seeds; the runner records the git commit and a dirty-tree flag in the manifest (C1); interior-`p` Pacman stochasticity is made reproducible by the shared seed-pin (Step 1).
- **Confound control:** the two arms share one weights dataclass for terminals+timestep, so they cannot drift; only `p` and the reward arm vary across the matrix; `--pacman-difficulty hard` and `--randomize-spawns` held constant. **Difficulty semantics (curriculum off):** with `--pacman-curriculum off`, `_build_pacman_policy` overrides the stage's default noise with `--pacman-random-action-prob` (our `p`), so `--pacman-difficulty hard` only fixes `pure_random=False` (defense-first heuristic) and `safe_distance = PACMAN_SAFE_DISTANCE` (=3, full flee horizon). Thus the *only* varying axis is `p` = fraction of steps Pacman acts randomly instead of evasively (`pacman_policy.py:96-100`); on the heuristic steps Pacman is the strongest evader. `safe_distance` is held constant across all points -- no planning-depth confound.
- **Right metric for an invariance-by-construction method:** headline the learning-speed metric (AULC / frames-to-threshold), not the asymptotic capture_rate (design-standards: report mean +/- std).
- **Fail-fast CLI (design-standards):** validate `p in [0,1]`, non-empty seeds/algorithms, and `--checkpoint-at-end` presence before launching expensive training.
- **Keyed, non-overwriting outputs (T2):** each `p` writes under `benchmarl_setup/runs/ab/p_<p>/`; both reward arms land in their own reward-keyed subfolders there.
- **Subprocess reuse:** the runner shells out to `run_benchmark.py`; no second training code path.
- **Privileged-info honesty:** `pursuit_fraction` uses Pacman's true position -- a training/eval-time metric only, consistent with the CTDE framing already documented for PBRS; state this in the docs.

## Design decisions

- **User-visible impact.** The researcher gains a reproducible A/B: a new `capture_v0_sparse_control` reward-id, an A/B runner (`run_reward_ab.py`) that executes the 2x3x5xN matrix in one command, a new `pursuit_fraction` column in the eval report, and an aggregator/plotter (`plot_reward_ab.py`) that emits the comparison table and presentation figures. Existing training/eval commands are unchanged except for the added eval column.
- **Trade-offs accepted.** Gained: a causally clean, statistically valid (>=5-seed) comparison with the correct sample-efficiency framing and a pursuit metric capture_rate cannot show. Given up: the matrix is compute-heavy (2 rewards x 3 algorithms x 5 seeds x 3 `p` = 90 training runs); mitigated by a configurable `--max-frames` and the ability to scope `--algorithms`/`--points` down. The control is a new code path that must be kept weight-locked to the PBRS arm (enforced by sharing the weights dataclass + a test).
- **Metacommunication impact.** The A/B runner prints, per point, the evasiveness `e = 1 - p`, the two arms being trained, and the save-folder, so I tell you exactly which condition is running. The plotter labels the two arms "esparso (controle)" and "esparso + PBRS" and annotates that the headline is learning speed, so the figure communicates the policy-invariance-aware framing directly. Use I/you phrasing in the docs.
