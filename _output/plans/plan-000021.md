## Agent Interpretation

**Problem**: The team-reward shaping pushes IQL ghosts into a *stay-still local optimum*. The `DISTANCE_DECREASE/INCREASE` signal is measured against a **stale** `last_pacman_sighting_position` (Pacman is rarely visible: 5×5 view on a 20×20 map), so random movement is anti-correlated with the cached target and ends up worse in expected value than standing still.

**Approach**: Implement research-12's recommendations scoped to *reward tuning* (the env reward function and its constants), as confirmed with the user:
- **R1 (potential-based shaping, true distance)** — replace the stale-sighting distance term with policy-invariant potential-based shaping `F(s) = -α · min_bfs_distance(ghosts → true Pacman position)`, reward `= F(s') − F(s)`. The reward function already has privileged access to `self.pacman.current_position` (used in `_is_capture_state`), so the shaping gradient is dense and correct at every step even while Pacman is unseen. Per Ng et al. (1999) this is policy-invariant and cannot introduce a new optimal-policy bias.
- **R3 (exploration bump)** — raise `VALID_MOVE` (0.01→0.05) and `ENTER_RECENTLY_UNVISITED_TILE` (0.05→0.15) so EV(move) > EV(stay) even where the potential gradient is flat (e.g. equidistant ghosts), removing any residual freeze incentive.
- **R4 (calibration test)** — add a unit test asserting `team_reward(move toward Pacman) > team_reward(stay still)` under the live reward function, locking in the fix and guarding against regression.

## Root cause

From research-12 RC1 (Critical): `_compute_team_reward()` ([pacman_environment.py:581-589](custom_environment/env/pacman_environment.py#L581-L589)) computes the distance reward against `target_position = self.last_pacman_sighting_position` — the *last place any ghost saw Pacman*. Because the BFS-evasion Pacman (PACMAN_SAFE_DISTANCE=5) flees and each ghost's 5×5 view covers ~6% of the 20×20 map, this target is stale on the majority of steps. `DISTANCE_INCREASE (−0.5)` therefore fires on a wrong target, making expected value of moving lower than `STAY_STILL (−0.03)`. With the terminal `+30` never reached in the ~300-episode budget, step-level shaping dominates and the policy collapses to inaction.

## Best practices

- **Potential-based reward shaping** (Ng, Harada & Russell 1999): defining the shaping as a difference of a state potential `F(s')−F(s)` guarantees the set of optimal policies is unchanged — safe to add a dense pursuit gradient without biasing the learned policy.
- Keep reward-term **signs unchanged** for existing terminal/penalty terms so the existing terminal-penalty smoke tests remain valid (consistent with the plan-000008 retuning note in `constant.py`).
- Leave the now-unused `DISTANCE_DECREASE`/`DISTANCE_INCREASE` enum members in place (no external/test references found) to avoid breaking imports; annotate them as superseded.
- Centralize the new coefficient as a named constant (no magic numbers); reuse the existing `_compute_min_distance_to_target()` and `_bfs_distance()` helpers rather than duplicating BFS.

## Design decisions

- **User-visible impact**: No CLI/interface change. Behaviorally, ghosts receive a smooth, correct pursuit gradient every step (even when Pacman is unseen) and a stronger incentive to keep moving, so training should escape the stay-still optimum and produce non-degenerate learning curves. The `info["reward_breakdown"]` key `distance_decrease/distance_increase` is replaced by `potential_shaping`; anyone reading `eval.py --show-reward-breakdown` will see the new term name.
- **Trade-offs accepted**: Gained a dense, policy-invariant pursuit signal and a non-freezing movement incentive. Gave up strict observation-honesty — the reward now uses the *true* Pacman position (privileged info the agent cannot observe). This is acceptable for reward shaping (the policy still acts only on its 5×5 view) but should be disclosed in any write-up that frames the work as pure partial observability.
- **Metacommunication impact**: The reward breakdown now communicates a single continuous `potential_shaping` term instead of the binary `distance_decrease/increase` pair — telling the researcher "here is how much closer/farther the team got to the real Pacman this step" rather than "a stale sighting got nearer/farther".

### Step 3: Replace stale-sighting distance term with potential-based shaping
In `_compute_team_reward()` ([pacman_environment.py:581-589](custom_environment/env/pacman_environment.py#L581-L589)), remove the `target_position = self.last_pacman_sighting_position` distance block and replace it with potential-based shaping on the **true** Pacman position:
```python
from custom_environment.env.domain.constant import POTENTIAL_SHAPING_ALPHA  # (import at module top)
# ... inside _compute_team_reward, where the old distance block was:
current_min_distance = self._compute_min_distance_to_target(self.pacman.current_position)
if current_min_distance is not None:
    phi = -POTENTIAL_SHAPING_ALPHA * float(current_min_distance)
    if self.last_potential is not None:
        add_term("potential_shaping", phi - self.last_potential)
    self.last_potential = phi
```
